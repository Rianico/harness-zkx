## Baseline Workflow

Baseline allows adopting stricter checks in existing codebases by only reporting errors on new or modified code.

### Enable Baseline

```bash
basedpyright --writebaseline
# Creates ./.basedpyright/baseline.json
```

### How It Works

Each baselined error is matched by:
- File path (relative to project root)
- Diagnostic rule name
- Error position (column only -- line-independent)

### Baseline Modes

| Mode | CLI Flag | Behavior |
|------|----------|----------|
| Default (local) | (none) | Auto-update when errors removed |
| Default (CI) | (none) | Lock mode -- exit non-zero if needs update |
| Write | `--writebaseline` | Always write new errors to baseline |
| Auto | `--baselinemode=auto` | Update only when errors removed |
| Lock | `--baselinemode=lock` | Never update, exit non-zero if stale |
| Discard | `--baselinemode=discard` | Read but never update |

### When to Manually Update Baseline

- A baselined error incorrectly resurfaces when updating unrelated code
- Enabling a new diagnostic rule and want to baseline the new errors

For other suppressions, use `# pyright: ignore[ruleName]`.

## Better Defaults

Basedpyright changes several defaults for stricter type checking out of the box.

### typeCheckingMode

**Pyright:** `"basic"` (minimal checking)

**Basedpyright:** `"recommended"` (all checks enabled)

- Less severe rules are warnings, not errors
- `failOnWarnings=true` by default in recommended mode
- Use baseline for gradual adoption

### pythonPlatform

**Pyright:** Current OS

**Basedpyright:** `"All"` (assume code runs on any platform)

### pythonPath

**Pyright:** Requires explicit configuration via `venv`/`venvPath` or `pythonPath`

**Basedpyright:** Auto-detects `.venv` at project root

If neither `pythonPath` nor `venvPath`/`venv` are set, basedpyright checks for `./.venv` and uses its Python interpreter.

## allowedUntypedLibraries

Suppress unknown type errors for specific untyped third-party libraries:

```toml
[tool.basedpyright]
allowedUntypedLibraries = ["requests", "old_lib"]
```

Suppresses for those modules:
- `reportUnknownVariableType`
- `reportUnknownMemberType`
- `reportMissingTypeStubs`

## Mypy vs Pyright: Design Goals

| Aspect | Mypy | Pyright |
|--------|------|---------|
| Architecture | Multi-pass, top-down | Lazy/JIT evaluation |
| Performance | Slower | 3x-5x faster on large codebases |
| Use case | CI-focused | Language server + CI |
| Parser | Python's parser | Custom parser with error recovery |

## Key Behavioral Differences

### Type Checking Unannotated Code

**Mypy:** Skips functions without annotations (unless `--check-untyped-defs`)

**Pyright:** Checks all code regardless of annotations

### Inferred Return Types

**Mypy:** Assumes `Any` for unannotated return types

**Pyright:** Infers return type from `return` statements

### Unions vs Joins

When merging types, pyright uses unions; mypy typically uses joins (common supertype):

```python
def func1(val: object):
    if isinstance(val, str):
        pass
    elif isinstance(val, int):
        pass
    else:
        return
    reveal_type(val)
    # mypy: object
    # pyright: str | int
```

### Variable Type Declarations

**Mypy:** First assignment is implicit declaration (unless `--allow-redefinition`)

**Pyright:** No implicit declaration; types are unioned across assignments

```python
def func1(condition: bool):
    if condition:
        x = 3
    else:
        x = ""  # Mypy error, pyright OK

    reveal_type(x)  # pyright: int | str
```

### Class and Instance Variables

**Mypy:** Does not distinguish between class and instance variables in all cases

**Pyright:** Distinguishes pure class vars, regular class vars, and pure instance vars

```python
class A:
    z: int = 0  # Regular class variable

print(A.z)  # OK
print(A().z)  # OK
a.z = 1  # Creates instance variable
```

### Type Guards

Pyright supports more guard expressions than mypy:
- `x == L` / `x != L` (literal comparison)
- `x in y` (container membership)
- `bool(x)` (truthiness check)
- Aliased conditional expressions

### Overload Resolution

**Mypy:** Returns `Any` when multiple overloads match due to `Any` argument

**Pyright:** Returns the supertype of all matching return types

```python
@overload
def func1(x: int) -> int: ...
@overload
def func1(x: str) -> float: ...

def func2(val: Any):
    reveal_type(func1(val))
    # mypy: Any
    # pyright: float (supertype of int and float)
```

## Inference Differences

### List/Set/Dict with Heterogeneous Types

```python
x = [1, 3.4, ""]
reveal_type(x)
# mypy: list[object]
# pyright: list[Unknown] or list[int | float | str] (with strict inference)
```

### Tuple with Literals

```python
x = (1, "stop")
reveal_type(x[1])
# mypy: str
# pyright: Literal["stop"]
```

### Assignment-Based Narrowing for Literals

```python
x: str | None
x = "a"
reveal_type(x)
# mypy: str
# pyright: Literal["a"]
```

### Literal Math

```python
def func(a: Literal[1, 2], b: Literal[2, 3]):
    c = a + b
    reveal_type(c)
    # pyright: Literal[3, 4, 5]
```

## Constructor Calls

**Pyright:** Follows runtime behavior -- evaluates `__new__` first, then `__init__` if `__new__` returns instance

**Mypy:** Evaluates `__init__` first, ignores `__new__` return type

## Import Statements

**Pyright:** Does not model import loader side effects (they depend on execution order)

**Mypy:** Models potentially unsafe side effects

```python
import http

def func():
    import http.cookies

x = http.cookies  # Runtime error
# mypy: allows
# pyright: error
```

## Plugins

**Mypy:** Supports plugins for library-specific type checking

**Pyright:** No plugin system

Rationale: Plugins have downsides (discoverability, maintainability, security, performance). Instead, work with typing community to extend the type system (e.g., PEP 681 `dataclass_transform`).

## Errors on Invalid Configuration

**Pyright:** May warn on invalid config, continues with exit code 0

**Basedpyright:** Exits with code 3 on any invalid configuration

```toml
[tool.pyright]
mode = "strict"  # Wrong! Should be typeCheckingMode
```

This typo would silently use basic mode in pyright. Basedpyright catches it.

## Migration Checklist

1. **Replace `# type: ignore`** with `# pyright: ignore[ruleName]`
2. **Set `typeCheckingMode = "recommended"`** in config
3. **Run `basedpyright --writebaseline`** to capture existing errors
4. **Review new diagnostic rules** (reportAny, reportExplicitAny, etc.)
5. **Add `allowedUntypedLibraries`** for third-party libs without types
6. **Update CI** to use `--baselinemode=lock` (default in CI environments)
