## Overview

Basedpyright adds 13 new diagnostic rules beyond what pyright provides. These rules are enabled by default in `recommended` and `all` modes.

| Rule | Recommended | All | Purpose |
|------|-------------|-----|---------|
| `reportAny` | warning | error | Ban all Any usage |
| `reportExplicitAny` | warning | error | Ban explicit Any annotations |
| `reportIgnoreCommentWithoutRule` | warning | error | Require rule in ignore comments |
| `reportPrivateLocalImportUsage` | warning | error | Check private imports in own code |
| `reportImplicitRelativeImport` | error | error | Ban implicit relative imports |
| `reportInvalidCast` | error | error | Detect casts to non-overlapping types |
| `reportUnsafeMultipleInheritance` | error | error | Warn on multiple bases with __init__ |
| `reportUnusedParameter` | warning | error | Report unused function parameters |
| `reportImplicitAbstractClass` | error | error | Require explicit ABC for abstract classes |
| `reportEmptyAbstractUsage` | warning | error | ABC with no abstract methods |
| `reportIncompatibleUnannotatedOverride` | none | error | Incompatible override of unannotated attr |
| `reportUnannotatedClassAttribute` | warning | error | Require annotations on class attrs |
| `reportInvalidAbstractMethod` | warning | error | abstractmethod on non-abstract class |
| `reportSelfClsDefault` | warning | error | self/cls with default value |

## reportAny

Pyright has rules for "Unknown" types (reportUnknownVariableType, etc.), but "Unknown" is not a real type -- it's a distinction pyright uses for `Any` from untyped code. There was no way to ban all `Any`.

```python
def foo(bar, baz: Any) -> Any:
    print(bar)  # reportUnknownVariableType error
    print(baz)  # No error in pyright
```

`reportAny` reports an error on any expression typed as `Any`:

```python
def foo(baz: Any) -> Any:
    print(baz)  # Error: reportAny
```

## reportExplicitAny

Similar to `reportAny`, but bans the `Any` type itself rather than expressions typed as `Any`:

```python
def foo(baz: Any) -> Any:  # Error: reportExplicitAny
    print(baz)  # Error: reportAny
```

## reportIgnoreCommentWithoutRule

It's good practice to specify the rule in ignore comments:

```python
# pyright: ignore[reportUnreachable]
```

This ensures new errors on the same line are not accidentally suppressed.

**Note:** `# type: ignore` comments are unsafe and disabled by default (`enableTypeIgnoreComments=false`). Use `# pyright: ignore` instead.

## reportPrivateLocalImportUsage

Pyright's `reportPrivateImportUsage` only checks third-party `py.typed` packages. This rule also checks your own code.

To re-export explicitly, use a redundant alias:

```python
# foo.py
from .some_module import a  # private import
from .some_module import b as b  # explicit re-export
```

```python
# bar.py
from foo import a  # Error: reportPrivateLocalImportUsage
from foo import b  # OK: explicitly re-exported
```

## reportImplicitRelativeImport

Pyright allows invalid imports that work when running a file directly but fail when imported as a module:

```python
# ./module_name/bar.py
import foo  # Wrong! Should be `from module_name import foo` or `from . import foo`
```

```python
# ./main.py
import module_name.bar  # ModuleNotFoundError: No module named 'foo'
```

The correct way:

```python
# ./module_name/bar.py
from . import foo  # Relative import
```

## reportInvalidCast

Most casts are to narrower or wider types. This rule detects casts to non-overlapping types:

```python
foo: int
cast(str, foo)  # Error: int and str do not overlap
```

**TypedDict Exception:** Casting between `dict` and `TypedDict` causes errors because `TypedDict` is not a subtype of `dict` in the type system.

## reportUnsafeMultipleInheritance

Multiple inheritance with multiple base classes that have `__init__` methods is unsafe:

```python
class Foo:
    def __init__(self):
        super().__init__()

class Bar:
    def __init__(self): ...

class Baz(Foo, Bar): ...  # Error: reportUnsafeMultipleInheritance

Baz()  # Foo.__init__ calls Bar.__init__ even though Foo doesn't extend Bar
```

This allows `reportMissingSuperCall` to be more lenient -- only reporting on classes that actually have a base class.

## reportUnusedParameter

Pyright greys out unused parameters (hint diagnostic). Basedpyright's rule supports all severity levels:

```python
def print_value(value: str):  # Error: reportUnusedParameter (warning)
    print("something else")
```

## reportImplicitAbstractClass

Abstract classes in Python are validated at runtime, not at definition. This rule requires explicit `ABC` for classes that don't implement all abstract methods:

```python
from abc import ABC, abstractmethod

class AbstractFoo(ABC):
    @abstractmethod
    def foo(self): ...

class FooImpl(AbstractFoo):  # Error: should extend ABC explicitly
    def bar(self):
        print("hi")

foo = FooImpl()  # Runtime error
```

Fix:

```python
class FooImpl(AbstractFoo, ABC):  # OK: explicit ABC
    def bar(self):
        print("hi")
```

## reportEmptyAbstractUsage

A class that extends `ABC` but has no abstract methods was likely intended to be abstract:

```python
from abc import ABC

class Foo(ABC):  # Abstract class with no abstract methods
    pass

foo = Foo()  # Error: reportEmptyAbstractUsage

class ConcreteFoo(Foo): ...
bar = ConcreteFoo()  # OK: subclass may be intentionally concrete
```

## reportIncompatibleUnannotatedOverride

Pyright's `reportIncompatibleVariableOverride` doesn't check unannotated base class attributes:

```python
class A:
    value = 1  # Inferred as int

class B(A):
    value = None  # No error in pyright, even though types differ
```

This rule reports the incompatibility.

**Note:** Disabled by default in `recommended` mode due to potential performance impact. Enable `reportUnannotatedClassAttribute` as an alternative.

Source: [basedpyright-expert-raw/020-new-diagnostic-rules.md](basedpyright-exp-raw/020-new-diagnostic-rules.md)

## reportUnannotatedClassAttribute

Requires type annotations on all class attributes that can be overridden:

```python
class A:
    value = 1  # Error: reportUnannotatedClassAttribute

class B(A):
    value: int = 1  # OK: explicit annotation
```

Useful when:
- Developing a library for pyright users
- Encountering performance issues with `reportIncompatibleUnannotatedOverride`
- Preferring explicit annotations to prevent API breakage

## reportInvalidAbstractMethod

Pyright ignores `@abstractmethod` on non-abstract classes:

```python
from abc import abstractmethod

class Foo:
    @abstractmethod
    def foo(self): ...  # No error in pyright

Foo()  # No error
```

This rule reports the error at the method definition, not at instantiation:

```python
class Foo:
    @abstractmethod
    def foo(self): ...  # Error: reportInvalidAbstractMethod
```

## reportSelfClsDefault

Specifying a default value for `self` or `cls` is almost certainly a mistake:

```python
class Foo:
    def foo(self=1): ...  # Error: reportSelfClsDefault
```
