## Tauri 2.0 ACL Architecture

Tauri 2.0 replaces the global v1 `allowlist` with a granular Access Control List (ACL) system.

Capabilities bind plugin and core permissions to target windows and webviews. App commands registered through `invoke_handler` are permitted by default unless `AppManifest::commands` narrows them.

```
┌────────────────────────────────────────────────────────┐
│               Capability (JSON File)                   │
│                                                        │
│  Windows: ["main"]                                     │
│  Permissions:                                          │
│    ├── "core:default"                                  │
│    ├── "opener:default"                                │
│    └── "fs:allow-read-text-file" (scoped)              │
└───────────┬────────────────────────────────────────────┘
            │ Enforces access on
┌───────────▼────────────────────────────────────────────┐
│              Webview Window ("main")                   │
└────────────────────────────────────────────────────────┘
```

## Capability File Structure

Define capabilities in JSON files under `src-tauri/capabilities/`.

```json
{
  "$schema": "../gen/schemas/desktop-schema.json",
  "identifier": "main-capability",
  "description": "Permissions for the primary application window",
  "windows": ["main"],
  "permissions": [
    "core:default",
    "opener:default",
    "dialog:allow-open",
    {
      "identifier": "fs:allow-read-text-file",
      "allow": [{ "path": "$APPDATA/**" }]
    }
  ],
  "platforms": ["macOS", "windows", "linux"]
}
```

### Capability Fields

| Field | Type | Description |
| ----- | ---- | ----------- |
| `identifier` | `string` | Unique identifier following ASCII kebab-case rules. Required. |
| `description` | `string` | Human-readable explanation of allowed actions. |
| `windows` | `string[]` | Window labels bound to this capability. Supports glob patterns like `"admin-*"`. |
| `webviews` | `string[]` | Specific webview labels when using multiwebview windows. |
| `permissions` | `PermissionEntry[]` | Array of permission identifiers or scoped permission objects. Required. |
| `platforms` | `string[]` | Target operating systems: `"macOS"`, `"windows"`, `"linux"`, `"android"`, `"iOS"`. |
| `local` | `boolean` | Activates permissions for local application URLs. Defaults to `true`. |
| `remote` | `object` | Specifies allowed remote URLs using URLPattern standards. |

## Permission Identifiers

Permission identifiers follow the `<plugin-name>:<permission-name>` format.

For core framework commands, use the `core:` prefix.

### Core Default Permissions

The `core:default` permission bundles basic application commands:
- `core:app:default`: Read application name, version, and identifiers.
- `core:event:default`: Listen, emit, and unlisten events (`listen`, `emit`, `emit_to`, `unlisten`).
- `core:image:default`: Create image instances and extract dimensions.
- `core:menu:default`: Manipulate menu items and popups.
- `core:path:default`: Resolve standard directories and join paths.
- `core:resources:default`: Close managed application resources.
- `core:tray:default`: Update tray icon and tooltip.
- `core:webview:default`: Query webview size and position.
- `core:window:default`: Window-state queries plus `internal-toggle-maximize`.

> [!IMPORTANT]
> `core:window:default` does NOT include `allow-show`, `allow-center`, or `allow-set-focus`. You must configure explicit permission grants for window mutations:
> - `core:window:allow-show`: Show hidden windows.
> - `core:window:allow-hide`: Hide visible windows.
> - `core:window:allow-center`: Center windows on screen.
> - `core:window:allow-set-focus`: Move focus to windows.
> - `core:window:allow-minimize`: Minimize windows.

### Plugin Permissions

Every official plugin defines a default permission bundle:
- `opener:default`: Open URLs and files with system default handlers.
- `fs:default`: Standard file system access operations.
- `dialog:default`: Display native file pickers and message boxes.
- `shell:default`: Spawn authorized external processes.

## Permission Scoping

Scopes restrict command parameters such as file paths or network endpoints.

Attach an `allow` or `deny` block to a permission entry:

```json
{
  "identifier": "fs:allow-read-file",
  "allow": [
    { "path": "$APPDATA/*" },
    { "path": "$RESOURCE/**" }
  ],
  "deny": [
    { "path": "$APPDATA/secrets/**" }
  ]
}
```

### Supported Path Variables

| Variable | Target Directory |
| -------- | ---------------- |
| `$APPDATA` | Application data directory (`appDataDir`) |
| `$APPCONFIG` | Application configuration directory (`appConfigDir`) |
| `$RESOURCE` | Bundled static resource directory |
| `$TEMP` | System temporary directory |
| `$HOME` | User home directory |
| `$DESKTOP` | User desktop folder |
| `$DOWNLOAD` | User downloads directory |

## Content Security Policy (CSP)

Define the Content Security Policy under `app > security > csp` in `tauri.conf.json`.

```json
{
  "app": {
    "security": {
      "csp": "default-src 'self'; img-src 'self' asset: http://asset.localhost; script-src 'self'; style-src 'self' 'unsafe-inline'"
    }
  }
}
```

The custom asset protocol uses `http://asset.localhost` by default. Set `app > security > assetProtocol > useHttpsScheme` to `true` when Windows compatibility requires secure HTTPS contexts.

Tauri automatically injects required IPC protocol nonces and scripts into the page header.

### CSP Best Practices

- Never use `'unsafe-eval'` in production builds.
- Restrict `default-src` to `'self'`.
- Restrict `connect-src` to explicit backend API hosts and `ipc:`.
- Host external assets on secure HTTPS origins.
