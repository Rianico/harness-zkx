## Framework integration

| Framework | How you get a Jinja environment                                                                                                                      |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| Flask     | Uses Jinja templates by default. Flask "sets up a Jinja environment and template loader for you" and provides helpers to render from view functions.   |
| Django    | Supports Jinja as its template engine. Wiring is documented by Django: <https://docs.djangoproject.com/en/stable/topics/templates/#support-for-template-engines>. |
| Babel     | Ships extractor entry point `jinja2.ext.babel_extract`; configure it in the Babel extraction method mapping file.                                      |
| Pylons    | You build the `Environment` in `config/environment.py` and attach it to Pylons app globals; render through `pylons.templating`.                         |

> [!NOTE]
> Only Flask wires the environment for you; elsewhere it is your responsibility (or Django's engine setting).

### Pylons

Configure the engine in `config/environment.py`, then render via `render_jinja` from `pylons.templating` ([008-integration.md](jinja-raw/008-integration.md)):

```python
from jinja2 import Environment, PackageLoader
config['pylons.app_globals'].jinja_env = Environment(
    loader=PackageLoader('yourapplication', 'templates')
)
```

> [!WARNING]
> The Pylons `c` object is non-strict by default: missing attributes return an empty string rather than an undefined object. Enable strict mode with `config['pylons.strict_c'] = True`.

### Babel extraction

Messages are extracted from **both** `trans` tags and code expressions.

## Django templates → Jinja

The syntax frequently looks the same, but "some work a bit differently".
Most likely to break a port: method calls, filter arguments, loop context, `cycle`.

| Aspect           | Django                                   | Jinja                                                  |
| ---------------- | ---------------------------------------- | ------------------------------------------------------ |
| Method calls     | Implicit, no parentheses: `user.get_created_pages` | Parentheses required, as in Python: `user.get_created_pages()` |
| Filter arguments | One literal, after a colon: `items\|join:", "` | Any positional/keyword args in parens: `items\|join(", ")` |
| Loop context     | `forloop`                                | `loop`                                                 |
| Loop counter     | `{{ forloop.counter }}`                  | `{{ loop.index }}`                                     |
| No-items block   | `{% empty %}`                            | `{% else %}`                                           |
| Alternating      | `{% cycle 'odd' 'even' %}`               | `loop.cycle('odd', 'even')`                            |

Jinja parentheses make it possible to pass variables to a method, "which is not possible in Django"; the same syntax calls macros.

```jinja
{% for page in user.get_created_pages() %}
    {{ loop.index }}. {{ page }}
{% else %}
    No items!
{% endfor %}
```

Filter arguments may be variables instead of literal values ([language](language.md) covers loops).

### Tests

Jinja has "tests", used with the `is` operator, in addition to filters.
That `is` is **not** the same as the Python operator. See [tests](tests.md).

```jinja
{% if user.user_id is odd %}
    {{ user.username|e }} is odd
{% else %}
    hmm. {{ user.username|e }} looks pretty normal
{% endif %}
```

### Cycle

Django's `{% cycle %}` tag becomes a method on the `loop` context.

```html+jinja
{% for user in users %}
    <li class="{{ loop.cycle('odd', 'even') }}">{{ user }}</li>
{% endfor %}
```

A cycler can also be assigned to a variable and used outside or across loops, via the `cycle()` global function.

## Mako → Jinja

Jinja can be reconfigured to look more like Mako ([009-switching.md](jinja-raw/009-switching.md)):

```python
env = Environment(
    block_start_string="<%",
    block_end_string="%>",
    variable_start_string="${",
    variable_end_string="}",
    comment_start_string="<%doc>",
    commend_end_string="</%doc>",
    line_statement_prefix="%",
    line_comment_prefix="##",
)
```

> [!WARNING]
> `commend_end_string` is spelled that way in the upstream docs; there is no `comment_end_string` parameter. Copy the snippet verbatim.

With that environment, Jinja "should be able to interpret a small subset of Mako templates without any changes".

### What still differs

| Mako construct                     | Jinja reality                                                                                          |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Embedded Python code               | Not supported. Move it out: preprocess data before rendering, or add a global function / filter.        |
| `<%def name="…">`                  | Called macros in Jinja; different syntax. Macros and `extends` live in [inheritance](inheritance.md).   |
| `<%inherit file="…"/>` inheritance | Template inheritance syntax differs; see [inheritance](inheritance.md).                                 |

### Worked conversion

The Mako original (`<%inherit>`, a `title()` def, a `% for item in list:` loop) becomes, under the configuration above:

```jinja
<% extends "layout.html" %>
<% block title %>Page Title<% endblock %>
<% block body %>
<ul>
% for item in list:
    <li>${item}</li>
% endfor
</ul>
<% endblock %>
```

**Done when:** you can name the environment source for your framework, and convert a Django `forloop`/`{% empty %}`/`{% cycle %}` block and a Mako `def` into Jinja equivalents without consulting the raw docs.
