## Null-default fallback — layout *or* standalone from one file

**Problem.** A page template normally extends `default.html`, but you also want to render the same file as a complete, standalone document (for previews, error pages, offline export).

**Pattern.** Put the `extends` tag inside an `if`, and keep a minimal skeleton after it.

```html+jinja
{% if not standalone %}{% extends 'default.html' %}{% endif -%}
<!DOCTYPE html>
<title>{% block title %}The Page Title{% endblock %}</title>
<link rel="stylesheet" href="style.css" type="text/css">
{% block body %}
  <p>This is the page body.</p>
{% endblock %}
```

**Why it works.** Jinja supports dynamic inheritance and does not distinguish between parent and child template as long as no `extends` tag is visited. When it is visited, the layout takes over and the markup around the blocks is discarded. `standalone` is undefined by default, and `not standalone` is true for an undefined name, so the layout branch is taken unless you pass `standalone=True`. [010-tricks.md](jinja-raw/010-tricks.md)

> [!WARNING]
> Jinja does not track parent/child before the first `extends`: *everything* written before that tag — including whitespace — is printed out instead of being ignored. Keep only the conditional `extends` (and its trailing whitespace trim marker) above the skeleton.

## Alternating rows — striped tables and lists

**Problem.** Every other row needs a different CSS class.

**Pattern.** Use the `cycle` method on the `loop` object.

```html+jinja
<ul>
{% for row in rows %}
  <li class="{{ loop.cycle('odd', 'even') }}">{{ row }}</li>
{% endfor %}
</ul>
```

**Why it works.** `cycle` can take an unlimited number of strings; each time this tag is encountered, the next item from the list is rendered. The counter is per-loop, so nested loops cycle independently. [010-tricks.md](jinja-raw/010-tricks.md)

## Highlighting active menu items

**Problem.** A shared navigation bar must mark the current page, but the nav markup lives in the layout template.

**Pattern.** Define the active page in the *child* template; give the layout a fallback.

```html+jinja
{% extends "layout.html" %}
{% set active_page = "index" %}
```

```html+jinja
{% set navigation_bar = [
    ('/', 'index', 'Index'),
    ('/downloads/', 'downloads', 'Downloads'),
    ('/about/', 'about', 'About')
] -%}
{% set active_page = active_page|default('index') -%}
...
<ul id="navigation">
{% for href, id, caption in navigation_bar %}
  <li{% if id == active_page %} class="active"{% endif %}>
  <a href="{{ href|e }}">{{ caption|e }}</a></li>
{% endfor %}
</ul>
```

**Why it works.** Assignments outside of `block`s in child templates are global and executed *before* the layout template is evaluated, so the layout can read `active_page`. The `|default('index')` filter keeps the layout renderable when no child sets the variable. `|e` escapes the attribute and text values; see [filters](filters.md). [010-tricks.md](jinja-raw/010-tricks.md)

> [!TIP]
> Unpacking the `(href, id, caption)` tuples directly in the `for` target keeps the loop body free of index arithmetic.

## Accessing the parent loop

**Problem.** Inside a nested loop you need data from the outer loop (for example a compound DOM id), but `loop` only exposes the innermost one.

**Pattern.** Alias the outer `loop` before entering the inner loop.

```html+jinja
<table>
{% for row in table %}
  <tr>
  {% set rowloop = loop %}
  {% for cell in row %}
    <td id="cell-{{ rowloop.index }}-{{ loop.index }}">{{ cell }}</td>
  {% endfor %}
  </tr>
{% endfor %}
</table>
```

**Why it works.** The special `loop` variable always points to the innermost loop, so the alias stored in `rowloop` is the only handle on the outer iteration. The alias must be assigned inside the outer loop body; elsewhere it would bind the wrong iteration. [010-tricks.md](jinja-raw/010-tricks.md)

## FAQ — design questions

### Why is it called Jinja?

"Jinja" is a Japanese Shinto shrine, or temple, and *temple* and *template* share a similar English pronunciation. It is not named after the city in Uganda. [011-faq.md](jinja-raw/011-faq.md)

### How fast is Jinja?

Jinja is relatively fast among template engines because it compiles and caches template code to Python code, so the template does not need to be parsed and interpreted each time; rendering becomes as close to executing a Python function as possible. Templates are cached by name after loading, and template loading itself uses a bytecode cache to avoid repeated compiling. Caches can be external to persist across restarts, and templates can be precompiled and loaded as fast Python imports. The docs state plainly that they dislike benchmarks, because engine defaults and tradeoffs differ and database access, API calls, and data processing usually dominate runtime. [011-faq.md](jinja-raw/011-faq.md)

### Isn't it a bad idea to put logic in templates?

You should try to remove as much logic as possible: less logic means a template that is easier to understand, has fewer potential side effects, and is faster to compile and render. But a template with no logic pushes all processing into code before rendering; Python's `string.Template` does exactly that and is fast but not convenient. Jinja's blocks, statements, filters, and function calls make expressive templates easy while still refusing arbitrary Python code or every Python language feature, which keeps the engine maintainable and templates readable. The docs put the balance in your hands. [011-faq.md](jinja-raw/011-faq.md)

### Why is HTML escaping not the default?

Escaping can be enabled, but is off by default because Jinja is a general purpose engine: it also generates plain text, LaTeX, emails, CSS, JavaScript, and configuration files, where HTML escaping makes no sense. Automatic escaping lowers the chance of an XSS problem but requires significant extra processing during compiling and rendering. Jinja uses MarkupSafe for escaping, which provides optimized C code for speed, yet the overhead of tracking escaping across methods and formatting remains. [011-faq.md](jinja-raw/011-faq.md)
