## The composition toolkit

Template inheritance is the "most powerful part of Jinja": a base skeleton defines **blocks** that children override. Tags take a template name string or a template object. [006-templates.md#template-inheritance](jinja-raw/006-templates.md)

| Tag                     | Role                                               | Context access                         |
| ----------------------- | -------------------------------------------------- | -------------------------------------- |
| `{% extends %}`         | Set the parent template                            | n/a                                    |
| `{% block %}`           | Placeholder *and* the content filling it           | outer vars hidden unless `scoped`      |
| `{% include %}`         | Render another template inline                     | current context by default             |
| `{% import %}`          | Bind a whole template as a namespace object        | globals only by default                |
| `{% from ... import %}` | Pull named macros/variables into current namespace | globals only by default                |
| `{% macro %}`           | Named, reusable renderable function                | own args + `varargs`/`kwargs`/`caller` |
| `{% call %}`            | Pass an anonymous block into a macro               | caller's context                       |

## Base + child: one complete layout

`base.html` defines four blocks; children fill the empty ones. [006-templates.md#base-template](jinja-raw/006-templates.md)

```html+jinja
<!DOCTYPE html>
<html lang="en">
<head>
    {% block head %}
    <link rel="stylesheet" href="style.css" />
    <title>{% block title %}{% endblock %} - My Webpage</title>
    {% endblock %}
</head>
<body>
    <div id="content">{% block content %}{% endblock %}</div>
    <div id="footer">
        {% block footer %}
        &copy; Copyright 2008 by <a href="http://domain.invalid/">you</a>.
        {% endblock %}
    </div>
</body>
</html>
```

The child overrides three blocks and keeps the parent's `footer`. [006-templates.md#child-template](jinja-raw/006-templates.md)

```html+jinja
{% extends "base.html" %}
{% block title %}Index{% endblock %}
{% block head %}
    {{ super() }}
    <style type="text/css">
        .important { color: #336699; }
    </style>
{% endblock %}
{% block content %}
    <h1>Index</h1>
    <p class="important">
      Welcome to my awesome homepage.
    </p>
{% endblock %}
```

## `extends` rules

- Must be the first tag — anything before it is printed normally and may cause confusion. [006-templates.md#child-template](jinja-raw/006-templates.md)
- Multiple `{% extends %}` tags may exist, but only one may execute at a time. [006-templates.md#extends](jinja-raw/006-templates.md)
- Name resolution depends on the loader: `FileSystemLoader` takes a filename, subdirectories use a slash (`{% extends "layout/default.html" %}`).
- A block is always filled whether the surrounding condition is true or false; `block` tags inside `if` execute regardless. [006-templates.md#base-template](jinja-raw/006-templates.md)
- Python may choose the parent: `env.get_template(...)` then `{% extends layout %}`. [006-templates.md#template-objects](jinja-raw/006-templates.md)

> [!WARNING]
> Two same-named `{% block %}` tags in one template are forbidden — a block also defines the content that fills the placeholder, so the parent could not tell which to use. [006-templates.md#child-template](jinja-raw/006-templates.md)

To render one block twice, call it through the special `self` variable: `{{ self.title() }}`. The "print before `extends`" behaviour is deliberate, not a bug — the **Null-Default Fallback** pattern in [recipes](recipes.md) depends on it. [006-templates.md#child-template](jinja-raw/006-templates.md)

## `super()` and nesting extends

`super()` returns the parent block's rendered result — `{% block sidebar %}{{ super() }}{% endblock %}` re-emits the parent's markup. [006-templates.md#super-blocks](jinja-raw/006-templates.md)

With multiple `{% extends %}` levels, `super` references chain — `super.super()` skips a level. [006-templates.md#nesting-extends](jinja-raw/006-templates.md)

```jinja
# parent.tmpl
body: {% block body %}Hi from parent.{% endblock %}

# child.tmpl
{% extends "parent.tmpl" %}
{% block body %}Hi from child. {{ super() }}{% endblock %}

# grandchild1.tmpl
{% extends "child.tmpl" %}
{% block body %}Hi from grandchild1.{% endblock %}

# grandchild2.tmpl
{% extends "child.tmpl" %}
{% block body %}Hi from grandchild2. {{ super.super() }} {% endblock %}
```

Documented outputs: `child.tmpl` → `body: Hi from child. Hi from parent.`; `grandchild1.tmpl` → `body: Hi from grandchild1.`; `grandchild2.tmpl` → `body: Hi from grandchild2. Hi from parent.` A block name may repeat after `endblock` for readability, but it must match. [006-templates.md#nesting-extends](jinja-raw/006-templates.md)

## Block scope and `required`

A block may **not** read outer-scope variables by default, so `{% for item in seq %}<li>{% block loop_item %}{{ item }}{% endblock %}</li>{% endfor %}` prints empty `<li>` items. Reason: if a child replaces the block, a variable would appear that was never defined in the block or passed to the context. [006-templates.md#block-nesting-and-scope](jinja-raw/006-templates.md)

Since Jinja 2.2, `{% block loop_item scoped %}` exposes the outer variables; an overriding child does **not** have to repeat the modifier. [006-templates.md#block-nesting-and-scope](jinja-raw/006-templates.md)

`required` blocks must be overridden at some point — not necessarily by the direct child. They may contain only space and comments, and cannot be rendered directly. [006-templates.md#required-blocks](jinja-raw/006-templates.md)

```jinja
# page.txt
{% block body required %}{% endblock %}
# issue.txt
{% extends "page.txt" %}
# bug_report.txt
{% extends "issue.txt" %}
{% block body %}Provide steps to demonstrate the bug.{% endblock %}
```

Rendering `page.txt` or `issue.txt` raises `TemplateRuntimeError`; `bug_report.txt` succeeds. With `scoped`, `required` must come after it: `{% block body scoped %}`, `{% block body required %}`, `{% block body scoped required %}`. [006-templates.md#required-blocks](jinja-raw/006-templates.md)

## Macros

Macros are Jinja's functions for DRY idioms; defaults are part of the signature. Macros from another template must be imported first. [006-templates.md#macros](jinja-raw/006-templates.md)

```html+jinja
{% macro input(name, value='', type='text', size=20) -%}
    <input type="{{ type }}" name="{{ name }}" value="{{
        value|e }}" size="{{ size }}">
{%- endmacro %}

<p>{{ input('username') }}</p>
```

| Name / attribute | Kind             | Holds / means                                              |
| ---------------- | ---------------- | ---------------------------------------------------------- |
| `varargs`        | inside a macro   | Extra positional arguments, as a list                      |
| `kwargs`         | inside a macro   | Unconsumed keyword arguments                               |
| `caller`         | inside a macro   | Callable macro, set when invoked from a `call` tag         |
| `name`           | on the macro     | `{{ input.name }}` prints `input`                          |
| `arguments`      | on the macro     | Tuple of accepted argument names                           |
| `catch_kwargs`   | on the macro     | `true` if the macro reads `kwargs`                         |
| `catch_varargs`  | on the macro     | `true` if the macro reads `varargs`                        |
| `caller`         | on the macro     | `true` if it reads `caller` and may be used from a call tag |

> [!WARNING]
> A macro in a child template does **not** override a same-named macro in a parent: with `foo` returning `LAYOUT` in `layout.txt` and `CHILD` in the extending `child.txt`, `{% block body %}{{ foo() }}{% endblock %}` prints `LAYOUT`. [006-templates.md#macros](jinja-raw/006-templates.md)

## `call` blocks

`call` passes a nameless macro into a macro, which invokes it as `caller()`. Arguments can be passed back — `{{ caller(user) }}` — making it a loop replacement. [006-templates.md#call](jinja-raw/006-templates.md)

```html+jinja
{% macro render_dialog(title, class='dialog') -%}
    <div class="{{ class }}">
        <h2>{{ title }}</h2>
        <div class="contents">
            {{ caller() }}
        </div>
    </div>
{%- endmacro %}

{% call render_dialog('Hello World') %}
    This is a simple dialog rendered by using a macro and a call block.
{% endcall %}
```

## `include`

`include` renders another template and outputs the result in place — `{% include 'header.html' %}`. [006-templates.md#include](jinja-raw/006-templates.md)

- The included template gets the current context by default; `without context` opts out (`with context` is valid but redundant). `ignore missing` suppresses a missing template and must precede any context visibility statement.
- A list is tried in order until one template is found, e.g. `{% include ['page_detailed.html', 'page.html'] %}`; combine with `ignore missing` if none may exist. A variable holding a name or template object is also accepted.
- The included template may `extend` and override blocks, but the current template cannot override blocks the include outputs.

[006-templates.md#include](jinja-raw/006-templates.md)

## `import` and `from ... import`

Imports behave like Python imports and are **cached**; imported templates see globals only, not the current template's variables. A helper module `forms.html` holding two macros: [006-templates.md#import](jinja-raw/006-templates.md)

```html+jinja
{% macro input(name, value='', type='text') -%}
    <input type="{{ type }}" value="{{ value|e }}" name="{{ name }}">
{%- endmacro %}
{%- macro textarea(name, value='', rows=10, cols=40) -%}
    <textarea name="{{ name }}" rows="{{ rows }}" cols="{{ cols }}">{{ value|e }}</textarea>
{%- endmacro %}
```

Importing the whole module gives attribute access; `from ... import` binds names directly, with optional aliasing. [006-templates.md#import](jinja-raw/006-templates.md)

```html+jinja
{% import 'forms.html' as forms %}
{{ forms.input('username') }}
{{ forms.textarea('comment') }}

{% from 'forms.html' import input as input_field, textarea %}
{{ input_field('password', type='password') }}
```

Macros and variables starting with one or more underscores are private. Since 2.4, a template object present in the context can be imported from. [006-templates.md#import](jinja-raw/006-templates.md)

## Import context behavior

The asymmetry is deliberate: includes get the current context, imports do not, because imports are cached and usually act as macro modules. The two explicit overrides are `{% from 'forms.html' import input with context %}` and `{% include 'header.html' without context %}`. [006-templates.md#import-context-behavior](jinja-raw/006-templates.md)

> [!NOTE]
> Adding `with context` or `without context` to an import/include directive passes the current context explicitly and **disables caching automatically**. [006-templates.md#import-context-behavior](jinja-raw/006-templates.md)

Since Jinja 2.1 an included template can see variables defined in the including template — `{% for box in boxes %}{% include "render_box.html" %}{% endfor %}` exposes `box`; in Jinja 2.0 it could not. [006-templates.md#import-context-behavior](jinja-raw/006-templates.md)
