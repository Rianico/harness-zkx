## What it is

**semantic-release** automates the whole package release workflow: determining the next version number, generating the release notes, and publishing the package. This removes the immediate connection between human emotions and version numbers — it strictly follows [Semantic Versioning](https://semver.org) and communicates the **impact** of changes to consumers.

### Highlights

- Fully automated release; new features and fixes immediately available to users
- Enforces SemVer; formalized commit-message convention documents codebase changes
- Notifies maintainers and users of new releases
- Publish on different distribution channels (e.g. [npm dist-tags](https://docs.npmjs.com/cli/dist-tag)) based on git merges
- Integrates with the CI workflow; supports any package manager/language via [plugins](https://semantic-release.org/foundation/plugins)
- Reusable config via [shareable configurations](https://semantic-release.org/usage/shareable-configurations)
- Supports [npm provenance](https://github.com/semantic-release/npm#npm-provenance) (signed attestations on GitHub Actions)

## Getting started — 3 steps

1. **Configure options and plugins** — see [Configuration](configuration.md). The scaffold writes `.releaserc.json` for you.
2. **Configure CI** — follow [CI Configuration](ci-configuration.md): choose a CI service, run `semantic-release` only after all tests pass, configure Git + package-manager auth.
3. **Run semantic-release** in the CI pipeline — `npx semantic-release` (pin the major: `npx semantic-release@25`). The scaffold's `release.yml` runs it via `workflow_dispatch`/`repository_dispatch`.

## How it works

### Commit message format

**semantic-release** reads commit messages to determine consumer impact. It defaults to [Angular Commit Message Conventions](https://github.com/angular/angular/blob/main/contributing-/commit-message-guidelines.md); the format can be changed via the `preset`/`config` options of [commit-analyzer](https://github.com/semantic-release/commit-analyzer#options) and [release-notes-generator](https://github.com/semantic-release/release-notes-generator#options).

Enforcement tools: [commitizen](https://github.com/commitizen/cz-cli) (authoring) and [commitlint](https://github.com/conventional-changelog/commitlint) (validation). The scaffold wires `commitlint` + `husky` for the latter.

Commit message → release type (default config):

| Commit message                                                          | Release type               |
| ----------------------------------------------------------------------- | -------------------------- |
| `fix(pencil): stop graphite breaking when too much pressure applied`    | ~~Patch~~ Fix Release      |
| `feat(pencil): add 'graphiteWidth' option`                              | ~~Minor~~ Feature Release  |
| `perf(pencil): remove graphiteWidth option` + `BREAKING CHANGE:` footer | ~~Major~~ Breaking Release |

> The `BREAKING CHANGE:` token must be in the **footer** of the commit.

### Automation with CI

**semantic-release** runs on the CI environment after every successful build on the release branch — no human directly involved, releases guaranteed unromantic and unsentimental.

### Triggering a release

Each new commit added to a release branch (`master`, `main`, `next`, `beta` — via push, PR merge, or branch merge) triggers a CI build that runs `semantic-release`; a release happens only if there are codebase changes since the last release that affect package functionality.

The scaffold's default is **on-demand**: `repository_dispatch` / `workflow_dispatch` only — no `push: tags` or `push: [main]` auto-release. Trigger manually via `gh api repos/<owner>/<repo>/dispatches -f event_type=semantic-release`.

### Release steps

After tests pass, `semantic-release` executes the [release steps](release-steps.md) in fixed order — from Verify Conditions through Notify. The scaffold's `.releaserc.json` plugins map onto them: `commit-analyzer` (Analyze) → `release-notes-generator` (Generate notes) → `changelog` (changelog file) → `git` (Create tag + Prepare + commit) → `github` (Publish + Notify). `@semantic-release/git` bumps `package.json` + `CHANGELOG.md` and commits + tags atomically — no manual `git tag` or manifest bump.

## Requirements

To use **semantic-release** you need:

- A [Git repository](https://git-scm.com)
- A CI service that allows [securely set up credentials](https://semantic-release.org/usage/ci-configuration#authentication)
- Git CLI **≥ 2.7.1** in the CI environment
- Node.js **≥ 22.14.0** in the CI environment

The scaffold's `release.yml` pins `setup-node` with `node-version: 24` and `actions/checkout` with `fetch-depth: 0` (tags needed for "Get last release").
