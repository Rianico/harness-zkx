# Extraction Rules for Reference Files

Rules for extracting, synthesizing, and referencing content in generated skill reference files. These replace line-count constraints with quality-driven extraction.

## Mandatory Metadata Header

Every generated reference file MUST begin with this metadata block:

```markdown
# <Skill Name> — <Module>

- **Version:** <version>
- **Date:** <generation-date>
- **Source:** <github/homepage URL>
- **Author:** <original author name>, Email: <email>
- **Generated by:** <scraper/converter name>, Email: <email>
- **Brief:** <one-sentence description of this module's scope>
```

- **Author** — Original author/maintainer of the documentation source
- **Generated by** — Who/what fetched and converted the docs into this skill

If any field is unavailable from the source, write `N/A` — this signals a knowledge gap, not an omission.

---

## Rule Set 1: Extraction (The Filter)

Extraction moves from "everything" to "the essentials" without losing context.

### Rule of Granularity (Atomic Data)

Extract information into the smallest logical units. It is easier to combine small pieces later than to break down a "wall of text" summary.

- Extract individual API signatures, not paragraph-length descriptions of an entire module
- Extract single configuration parameters, not configuration blocks
- Extract one pattern per entry, not "common patterns" sections

### Source-to-Row Link

Every piece of extracted data MUST carry a source reference. If a quote appears in a summary, it must immediately follow a reference to the source file name and section.

```markdown
`wt switch --create feature` — [commands.md#switch](worktrunk-guide-raw/commands.md)
```

**Format:** `[display text] — [source anchor](raw-docs-path)`

### Objective Coding

Label extracted data based on facts, not interpretations:

| Good Tag | Bad Tag |
|----------|---------|
| `[CLI_Command]` | `[Useful_Feature]` |
| `[Config_Parameter]` | `[Important_Setting]` |
| `[Hook_Type]` | `[Cool_Automation]` |
| `[Error_State]` | `[Bad_Thing]` |

### Schema First

Define a target schema before extracting. Choose from the templates below based on document type. Do not deviate from the chosen schema to ensure consistency across the set.

## Rule Set 2: Synthesis & Clarity (The Product)

Reference files prioritize the reader's time. They simplify the complex rather than restating it.

### Bottom-Up Synthesis

Group extracted atomic notes into themes first, then write summaries based on those groups. This prevents confirmation bias — seeing only what you expect to see.

1. Extract all atomic data points
2. Cluster into themes (by function, by workflow, by error type)
3. Write synthesis from the clusters, not from expectations

### One-Idea-Per-Paragraph

Each paragraph covers exactly one point. Keep sentences under 25 words.

**Bad:**
> The switch command allows you to switch between worktrees and it supports several shortcuts like ^ for the default branch, @ for current, and - for previous, plus you can create new worktrees with --create.

**Good:**
> `wt switch` changes the active worktree by branch name. Shortcuts: `^` (default branch), `@` (current), `-` (previous).

### Signal Phrases

Use clear attributions to distinguish between analysis and raw data:

- "The documentation states..." — direct claim from source
- "This implies..." — inference from extracted data
- "Source 04-A contradicts Source 02-B on..." — conflicting information
- "Pattern observed across..." — synthesis from multiple sources

## Rule Set 3: Referencing & Traceability (The Proof)

A reference file is only as good as its ability to be verified.

### Golden Source Rule

Always link back to the original raw doc, never a secondary summary. This prevents "telephone game" errors.

- In **prose text** (instructions, "read X" guidance): use `$SKILL_DIR/references/<skill-name>-raw/` — cwd is unknown to the reader
- In **markdown links** (inline source references): use relative paths like `[text](worktrunk-guide-raw/file.md)` — standard relative-to-file convention
- Never link to another curated reference file as the source of truth

### Lineage Documentation

The SKILL.md references table serves as the master index. Each reference file's metadata header maps back to its raw docs source.

```markdown
## References

| Module | File | Source | Topics |
|--------|------|--------|--------|
| commands | `$SKILL_DIR/references/commands.md` | `references/worktrunk-guide-raw/switch.md` | switch, list, remove, merge |
```

### Source Linking

Every referenced finding must link to its raw doc location. Use inline links:

```markdown
See [switch command](worktrunk-guide-raw/switch.md) for full flag reference.
```

### Independent Verification

For high-stakes content (security parameters, destructive operations, breaking changes), cross-reference against the raw docs before including in curated references.

## Template Schemas

Choose the appropriate schema based on document type. Each schema defines required headers — fill every header. If a header has no data in the source, write `N/A` to signal the gap.

### 1. Technical Documentation (Systems & Architecture)

For hardware specs, system overviews, or complex software deployments.

```markdown
## [System/Component Name]
- **Status:** (Draft/Active/Deprecated)
- **Version/Release:**
- **Owner/Maintainer:**

### Overview
> 2-sentence summary of what this system does and its primary goal.

### Specifications & Requirements
- **Prerequisites:** (What must be true before using this?)
- **Dependencies:** (What other systems does this rely on?)
- **Constraints:** (Hardware limits, time limits, or budget constraints.)

### Architecture/Logic
- **Input:**
- **Processing Logic:**
- **Output:**

### Configuration Parameters
| Parameter | Type | Default | Description |
| :--- | :--- | :--- | :--- |
| `Key` | String/Int | Value | Explanation |

### Troubleshooting & Error States
- **Common Failure 1:** [Symptom] -> [Resolution]
- **Verification:** (How to prove it is working correctly?)

### References
- [Ref 01]: (Link to raw data source)
```

### 2. Programming & CLI Reference

For capturing syntax, library functions, or terminal commands.

```markdown
## Command/Function: `name`
- **Library/Package:**
- **Language/Shell:**

### Syntax
```[language]
command [flags] [arguments]
```

### Description
- Purpose of the command.
- Side effects (e.g., "This deletes files permanently").

### Parameters & Flags
- `-f, --flag`: Description (Required/Optional)
- `-v, --verbose`: Description

### Practical Examples
1. **Basic Use:** `command argument`
2. **Advanced Chain:** `command | grep 'x'`
3. **Recovery/Undo:** How to reverse this action.

### Common Pitfalls
- [Source Ref]: Note on why this fails in certain environments.

### Related Commands
- [[See Also]]
```

### 3. Life Principles & Philosophical Guidelines

For extracting wisdom from books, podcasts, or personal reflections.

```markdown
## Principle: [Name of the Rule]
- **Domain:** (Health / Finance / Social / Mental)
- **Origin:** (Author/Source Name)

### The Core Tenet
> The "One Sentence" summary of the belief or rule.

### Application Context
- **When to use this:** (e.g., "When feeling overwhelmed by choice.")
- **When NOT to use this:** (The boundary conditions or exceptions.)

### Actionable Steps (The "How")
1. Step one...
2. Step two...

### Evidence & Mental Models
- **Supporting Data:** (Stats or anecdotes from the raw material.)
- **Counter-Arguments:** (What are the risks of following this blindly?)

### Traceability
- **Source:** [Ref ID] - Page/Timestamp
- **Cross-Link:** [[Related Principle]]
```

### 4. Productivity & Workflow Optimization

For documenting a new "way of working" or a specific app setup.

```markdown
## Workflow: [Name of Process]
- **Objective:** (e.g., "Reach Inbox Zero" or "Process Research Notes")
- **Frequency:** (Daily / Weekly / As Needed)

### Tooling Stack
- **Primary Tool:**
- **Secondary/Integration Tool:**

### The Process Map
1. **Trigger:** (What starts this workflow?)
2. **Action 1:**
3. **Action 2:**
4. **Conclusion:** (What is the "Definition of Done"?)

### Optimization Rules
- **The "Rule of [X]":** (e.g., "If it takes < 2 mins, do it now.")
- **Batching:** How to group tasks to save energy.

### Maintenance
- How to review this workflow for efficiency once a month.

### References
- Derived from: [Book Title/Article URL]
```

### 5. Research & Literature Review (Data Extraction)

For reading through many papers/articles to find a specific answer.

```markdown
## Source: [Title/Author]
- **ID:** (e.g., REF-001)
- **Topic Tags:** #tag1 #tag2

### Key Claims/Findings
- **Claim A:** The central argument.
- **Claim B:** Supporting argument.

### Methodology/Data
- **Method:** How did they find this out? (Survey, Experiment, Meta-analysis)
- **Sample Size/Scope:**

### Quotes & Citations
> "Direct quote from the raw material that is particularly impactful." (Page #)

### Critique/Limitations
- What did the author miss?
- Are there biases present in the source?

### Relation to Project
- How does this specific source change my current understanding?
```

## Quick-Reference Quality Checklist

Before finalizing any reference file, verify:

| Signal | Check |
|--------|-------|
| Metadata header | Version, date, source, author, generated by, brief present |
| Schema compliance | File follows a template schema from this document |
| Source linking | Key claims link back to raw docs |
| Atomic extraction | Individual API signatures, not wall-of-text summaries |
| Code examples intact | Never split code blocks across files |
| Context for API docs | "When to use" and "Common patterns" sections included |

## Schema Selection Guide

| Doc Type | Schema | Typical Skills |
|----------|--------|---------------|
| CLI tools | Programming & CLI Reference | worktrunk-guide, git-flow |
| Libraries/Frameworks | Programming & CLI Reference | ui-framework-guide, async-runtime-guide |
| System Architecture | Technical Documentation | deployment-patterns, infra-guides |
| Methodology/Process | Productivity & Workflow Optimization | tdd-cycle, eval-gate |
| Research/Analysis | Research & Literature Review | deep-research |
| Principles/Wisdom | Life Principles & Philosophical Guidelines | kaizen-why |

Most technical skills will use schemas 1 and 2. Schema 3-5 apply to knowledge-work skills.

---

## How to Use These Rules

1. **Before extraction:** Choose the appropriate schema for each reference file
2. **During extraction:** Apply Rule Set 1 (atomic data, source linking, objective coding)
3. **During synthesis:** Apply Rule Set 2 (bottom-up, one-idea-per-paragraph, signal phrases)
4. **After generation:** Apply Rule Set 3 (golden source, lineage, verification)
5. **Every file:** Include the mandatory metadata header with version, date, source, author, brief
